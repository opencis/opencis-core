## 1. CXL Protocol Fundamentals

### Q1.1 — What is CXL and why does it matter for modern data-center architectures?

**Answer:**  
CXL (Compute Express Link) is an industry-open, high-speed interconnect standard built on top of PCIe physical infrastructure. It is designed to address the **memory wall** problem in heterogeneous computing. Three features make it strategically important:

1. **Memory Expansion**: Hosts can address CXL-attached memory as regular system RAM (Type 3 devices), breaking DRAM DIMM slot limitations.
2. **Cache Coherency**: Devices can hold cached copies of host memory (Type 1/2) with hardware-maintained coherency, removing the need for explicit software cache flushes.
3. **Memory Sharing**: CXL 3.0/4.0 introduces peer-to-peer and shared-memory pools (via MLDs and the fabric switch), enabling memory disaggregation at rack scale.

In `opencis-core`, the framework simulates this full protocol stack in pure Python/asyncio so firmware and driver teams can validate behaviour without physical silicon.

---

### Q1.2 — Explain the three CXL sub-protocols and which device types support each.

**Answer:**

| Sub-Protocol | Direction | Purpose | Device Types |
|---|---|---|---|
| **CXL.io** | Bidirectional | PCIe-compatible config space (CFG_RD/CFG_WR), MMIO reads/writes (MRD/MWR), completions | T1, T2, T3 |
| **CXL.cache** | Device→Host | Device caches host memory; uses snoop messages (H2D: Snoop, D2H: Response, Request) | T1, T2 |
| **CXL.mem** | Host→Device | Host accesses device memory; uses M2S (Master-to-Subordinate) and S2M channels | T2, T3 |

In `opencis-core`, the `CxlPacketProcessor` selects which FIFOs to wire based on `CXL_COMPONENT_TYPE` (e.g., T1 gets CXL.cache only, T2 gets both, D2 gets CXL.mem only).

---

### Q1.3 — What is a TLP and how does the CXL simulator represent it?

**Answer:**  
A **TLP** (Transaction Layer Packet) is the fundamental unit of transfer in PCIe/CXL. It consists of a header and optional data payload. In `opencis-core`:

- All packets share a common `SystemHeader` (2 bytes) with a `payload_type` field that demuxes the packet kind (`CXL_IO=1`, `CXL_CACHE=2`, `CXL_MEM=3`, `CCI=4`, `PBR=5`).
- Field layouts are declared in `fields.py` as a list of `(name, start_bit, width_bits)` tuples.
- These declarations drive a **code-generator** (`generate_packet_structs.py`) that emits Cython `.pyx` accessors for performance. A pure-Python fallback (`packet_structs.py`) is generated by `generate_py_fallback.py` when Cython cannot be compiled.
- Composite packet classes (e.g., `CxlIoMemRdPacket`, `PbrBasePacket`) reference field offsets from the shared byte buffer.

---

### Q1.4 — How does CXL differ from standard PCIe in terms of the transaction model?

**Answer:**

| Aspect | PCIe | CXL |
|---|---|---|
| Coherency | Software-managed (no hardware snoop) | Hardware snoop via CXL.cache |
| Memory access | MMIO only (memory-mapped registers) | Full byte-granular memory access via CXL.mem |
| Ordering | Strict PCIe ordering rules | Relaxed ordering modes possible on CXL.mem |
| Fabric | Point-to-point or classic switch | CXL 4.0 adds Fabric (PBR, GFD, pooled memory) |
| Protocol types | Single (TLP) | Three sub-protocols sharing one physical link |

## 2. System Architecture & Design Patterns

### Q2.1 — Describe the overall layered architecture of `opencis-core`.

**Answer:**  
The simulator is organized into four conceptual layers:

```
┌────────────────────────────────────────────┐
│  Application Layer  (opencis/apps/)        │
│  CxlSwitch, SingleLogicalDevice,           │
│  MultiLogicalDevice, Accelerator, FM        │
├────────────────────────────────────────────┤
│  Component Layer  (opencis/cxl/component/) │
│  CxlPacketProcessor, HdmDecoder,           │
│  PbrSwitchRouter, CacheController, FMLD    │
├────────────────────────────────────────────┤
│  Transport Layer  (opencis/cxl/transport/) │
│  Packet structs, CCI packets, fields.py    │
├────────────────────────────────────────────┤
│  Infrastructure  (opencis/util/, opencis/pci/) │
│  RunnableComponent, Logger, FifoPair       │
└────────────────────────────────────────────┘
```

- **Application layer** composes components and exposes CLI/Socket.IO APIs.
- **Component layer** contains stateful logic (routing, cache, memory management).
- **Transport layer** is purely structural—packet serialization and field access.
- **Infrastructure** provides generic async lifecycle, logging, and FIFO primitives.

---

### Q2.2 — What is `RunnableComponent` and why is it used pervasively?

**Answer:**  
`RunnableComponent` is a base class in `opencis/util/component.py` that standardises the async lifecycle of every long-running component:

```python
class RunnableComponent:
    async def run(self): ...          # starts _run() as an asyncio task
    async def stop(self): ...         # triggers _stop(), waits for clean exit
    async def _run(self): ...         # override: main coroutine
    async def _stop(self): ...        # override: send shutdown signal
    async def wait_for_ready(self): ...   # caller waits until _change_status_to_running()
```

**Why it matters architecturally:**
- Uniform `run()/stop()` contract means the application layer can start and stop any component without knowing its internals.
- `wait_for_ready()` lets parent components synchronize startup order (e.g., `CxlPacketProcessor` waits for FMLD to be ready before itself transitions to RUNNING).
- It removes ad-hoc threading/task management boilerplate from domain code.

---

### Q2.3 — How is inter-component communication achieved inside the simulator?

**Answer:**  
The simulator uses **asyncio `Queue`-based FIFO pairs** (`FifoPair`) rather than shared state. Each logical channel (CFG, MMIO, CXL.mem, CXL.cache, CCI) has a `host_to_target` queue and a `target_to_host` queue. This design:

1. **Decouples producers from consumers** — no lock contention.
2. **Models hardware** — in real CXL, each sub-protocol has independent credit-based channels.
3. **Enables clean shutdown** — a sentinel `None` (or a `CONNECTION_DISCONNECTED` sideband packet) signals termination without cancelling tasks.
4. **Makes unit testing trivial** — tests enqueue packets and assert on dequeued results, no mocking required.

---

### Q2.4 — What is the `FMLD` and where does it sit architecturally?

**Answer:**  
`FMLD` (FM-Owned Logical Device interface) handles the CCI (Component Command Interface) protocol for Multi-Logical Devices. Architecturally it lives inside `CxlPacketProcessor` when the component type is `CXL_COMPONENT_TYPE.LD`:

```
Host ──CCI packets──► CxlPacketProcessor (LD mode)
                           │
                           ▼
                         FMLD
                    (upstream CCI FIFO)
                           │
                    handles: GET_LD_INFO
                             GET_LD_ALLOCATIONS
                             SET_LD_ALLOCATIONS
```

The FMLD runs as a separate async task inside the packet processor's `_run()`, and `CxlPacketProcessor` calls `await self._fmld.wait_for_ready()` before itself transitioning to RUNNING, enforcing correct startup order.

---

### Q2.5 — Explain the Singleton pattern used in `MLDManager` and its trade-offs.

**Answer:**  
`MLDManager` uses Python's `__new__`-based Singleton:

```python
class MLDManager:
    _instance = None
    def __new__(cls):
        if cls._instance is None:
            cls._instance = super().__new__(cls)
        return cls._instance
```

**Purpose:** One global registry of port→MLD mappings, accessible from any part of the system (CCI handlers, Socket.IO server, test helpers).

**Trade-offs:**

| Advantage | Disadvantage |
|---|---|
| Simple global access from anywhere | Hard to test in isolation; state leaks between tests |
| Mirrors real hardware (one FM per rack) | Thread/process safety assumptions (asyncio single-thread OK, but fragile if multiprocessed) |
| No dependency injection plumbing needed | Cannot run multiple independent switch topologies in the same process |

**Interview follow-up:** A better design for testability would be to inject an `MldRegistry` interface via the constructor, keeping the singleton only at the application entry point.

## 3. Transport Layer & Packet Processing

### Q3.1 — Walk through how a CXL.io Memory Read packet is processed from wire bytes to a FIFO.

**Answer:**  
End-to-end flow through `CxlPacketProcessor._process_incoming_packets()`:

1. `PacketReader.get_packet()` reads raw bytes from the TCP `StreamReader`.
2. The first 2 bytes (SystemHeader) are inspected: `payload_type == CXL_IO (1)`.
3. The raw bytes are cast to `CxlIoBasePacket`.
4. `cxl_io_packet.is_mmio()` checks `fmt_type` field (e.g., `MRd 32/64`).
5. Since it's a request (not a completion), `_push_tlp_table_entry()` records `(transaction_id << 8) | ld_id → CXL_IO_FIFO_TYPE.MMIO` in `_tlp_table`.
6. The packet is placed on `self._incoming.mmio` (an asyncio Queue).
7. Downstream, the MMIO manager dequeues it, looks up the address in the HDM decoder, reads from the backing memory file, and enqueues a completion on `self._outgoing.mmio`.
8. `_process_outgoing_mmio_packets()` dequeues the completion, calls `_pop_tlp_table_entry()` to clean up state, and calls `self._writer.write(bytes(packet))`.

**Key design point:** The TLP table (`_tlp_table`) acts as an in-flight tracker, associating completions with the correct FIFO (CFG or MMIO) even when out-of-order responses arrive.

---

### Q3.2 — Why does the project use both Cython and a pure-Python fallback for `packet_structs`?

**Answer:**  
Packet field access is the hottest code path — every TLP processed requires multiple bit-field reads and writes. Cython compiles `packet_structs.pyx` to a native `.pyd` extension, reducing field access overhead by ~10x.

However, Cython requires a C compiler (MSVC on Windows, GCC on Linux). In environments without a compiler (CI containers, developer machines), `generate_py_fallback.py` produces `packet_structs.py` — a complete pure-Python equivalent. Python's import system auto-prefers the `.pyd` extension when it exists:

```
import packet_structs  →  Python checks for .pyd/.so first, then .py
```

**Critical correctness issue fixed during development:** Pure-Python field accessors must account for the struct's byte offset within the shared parent buffer:

```python
# Wrong: ignores where in the buffer this struct starts
return _read_bits(self._parent_buf, field_start, field_width)

# Correct: shifts by the struct's byte position
return _read_bits(self._parent_buf, self._p * 8 + field_start, field_width)
```

Without this fix, all field reads in composite packets (e.g., PBR header inside a buffer that also contains a SystemHeader) are corrupted.

---

### Q3.3 — How does the TLP table handle MLD scenarios where multiple Logical Devices share one TCP connection?

**Answer:**  
In standard (SLD) mode, the TLP table key is `transaction_id << 8`. For MLD mode (`CXL_COMPONENT_TYPE.LD`), the key is `(transaction_id << 8) | ld_id`, where `ld_id` comes from `cxl_io_packet.tlp_prefix.ld_id`.

**Exception for USP and Root Port:** Since USP/R component types are "LD-agnostic" (they don't see LD-ID tagging), the code always forces `ld_id = 0`:

```python
if self._component_type in (CXL_COMPONENT_TYPE.USP, CXL_COMPONENT_TYPE.R):
    ld_id = 0
else:
    ld_id = cxl_io_packet.tlp_prefix.ld_id
```

This ensures push/pop operations on the TLP table use the same key derivation logic, preventing mismatches when completions arrive.

---

### Q3.4 — What is the `PbrBasePacket` and how does zero-copy decapsulation work?

**Answer:**  
`PbrBasePacket` is a composite packet with a 6-byte header (2B SystemHeader + 4B PbrHeader) prepended to an inner HBR TLP. The PBR header carries 12-bit SPID and DPID fields.

**Zero-copy encapsulation:**

```python
@staticmethod
def encapsulate(spid: int, dpid: int, inner_packet: BasePacket) -> PbrBasePacket:
    pbr = PbrBasePacket.create(spid, dpid)
    pbr._inner_packet = inner_packet   # stash reference, no byte copy
    return pbr
```

**Zero-copy decapsulation at egress:**

```python
inner_packet = getattr(pbr_packet, "_inner_packet", None)
if inner_packet is None:
    # Wire path: reconstruct from raw bytes (one allocation)
    payload_offset = pbr_packet.get_payload_offset()
    inner_packet = BasePacket(bytes(pbr_packet)[payload_offset:])
```

The stash avoids re-parsing bytes when the packet was constructed locally (in-process simulation path). The wire path (packet arrived from a TCP socket) falls back to byte slicing, incurring one allocation.

## 4. HDM Decoder & Address Translation

### Q4.1 — What is an HDM decoder and why is it needed?

**Answer:**  
An **HDM (Host-managed Device Memory) Decoder** maps a range of Host Physical Addresses (HPA) to a physical device's Device Physical Address (DPA). Without it, the host OS cannot distinguish which CXL memory device owns a given physical address.

In `opencis-core`, three decoder variants are implemented:

| Class | Use Case |
|---|---|
| `DeviceHdmDecoderManager` | Type-3 memory device — maps HPA→DPA |
| `SwitchHdmDecoderManager` | Virtual Switch — maps HPA→downstream port |
| `PbrHdmDecoderManager` | PBR Switch — maps HPA→DPID for PBR encapsulation |

All share `HdmDecoderManagerBase` which provides: `get_decoder_from_hpa()`, `is_hpa_in_range()`, `commit()`, and `get_decoder_count()`.

---

### Q4.2 — Walk through the HPA→DPA translation math.

**Answer:**  
For a `DeviceHdmDecoder` with interleaving:

```
HPA offset = HPA - decoder.base
Low bits   = HPA_offset[0 .. ig+7]           (below the interleave granularity boundary)
High bits  = HPA_offset[ig+8+iw .. 51]       (above the interleave selection bits)
DPA offset = Low bits | (High bits << (ig+8))
DPA        = DPA offset + dpa_base
```

Where:
- `ig` = interleave granularity (0=256B, 1=512B, … 6=16KB)
- `iw` = interleave ways (0=1-way, 1=2-way, … 4=16-way)

The interleave selection bits `HPA[ig+8 .. ig+8+iw-1]` identify which device in a multi-device interleave set owns this chunk — they are stripped from the DPA.

For non-power-of-two interleaving (3/6/12-way), the formula uses integer division by 3:
```python
dpa_offset_high = get_bit_range(hpa_offset, self.ig + self.iw, 51) // 3
```

---

### Q4.3 — How does `SwitchHdmDecoder` decide which downstream port to forward to?

**Answer:**

```python
def get_target(self, hpa: int) -> int:
    decoded_ig = 1 << (self.ig + 8)          # interleave granularity in bytes
    decoded_iw = 1 << self.iw                 # number of ways
    target_index = (hpa // decoded_ig) % decoded_iw
    return self.target_ports[target_index]
```

The HPA is divided by the interleave granularity to get the "stripe number", then modulo the number of ways selects which port in `target_ports` serves this stripe. This implements striped interleaving across downstream ports — a standard technique for maximizing memory bandwidth.

---

### Q4.4 — What is the difference between `PbrHdmDecoderManager` and `PbrSwitchManager`?

**Answer:**  
This is a **separation of concerns** between data plane and control plane:

| Component | Layer | Responsibility |
|---|---|---|
| `PbrHdmDecoderManager` | **Data plane** | Address translation: HPA → DPID at ingress. Used inside `PbrSwitchRouter._route_packet()` for every packet. |
| `PbrSwitchManager` | **Control plane** | CCI state store: PID table, DRT, PID bindings. Modified only when the Fabric Manager sends CCI commands. |

The router queries `PbrHdmDecoderManager.get_dpid(address)` to determine the DPID for HBR-to-PBR encapsulation, then queries `PbrSwitchManager.get_drt(drt_index, dpid, 1)` to resolve which physical port to forward to. The two components are independently testable and independently updateable.

## 5. Port-Based Routing (PBR) — CXL 4.0

### Q5.1 — Explain PBR and how it differs from Host-Based Routing (HBR).

**Answer:**

| Aspect | HBR (Host-Based Routing) | PBR (Port-Based Routing) |
|---|---|---|
| Who drives routing | Host OS via PCIe enumeration | Fabric Manager via CCI commands |
| Routing key | PCIe Bus/Device/Function (BDF) | 12-bit Port ID (PID/DPID) |
| Flexibility | Topology fixed at boot | Dynamic re-routing possible at runtime |
| Spec version | PCIe / CXL 1.x–3.x | CXL 4.0 §7.7.13 |
| Host OS awareness | Fully aware of topology | Host sees "fabric node", not individual ports |

**PBR workflow:**
1. FM assigns PIDs to physical ports (`Configure PID Assignment` opcode `0x5704`).
2. FM programs the DPID Routing Table (`Set DRT` opcode `0x5709`): DPID → egress port.
3. At ingress, the switch encapsulates HBR TLPs in a PBR header (SPID, DPID).
4. The router performs a DRT lookup on DPID and forwards the inner TLP to the egress port.

---

### Q5.2 — Trace a memory-write packet from QEMU through the PBR switch to the GFD.

**Answer:**

```
1. QEMU/Host issues HBR MWR TLP targeting addr 0x1500
   system_header.payload_type = CXL_IO (1)

2. Packet arrives at port_fifos[0].host_to_target  (USP ingress)

3. PbrSwitchRouter._process_port_host_ingress(port=0, packet)
   → _route_packet(ingress_port=0, packet, "host_to_target")

4. base_packet.is_pbr() == False  →  HBR path
   address = cast(CxlIoMemReqPacket, packet).get_address()  → 0x1500

5. PbrHdmDecoderManager.get_dpid(0x1500)  → DPID = 0x200

6. PbrBasePacket.encapsulate(spid=0, dpid=0x200, inner_packet=pkt)
   → PBR TLP: SystemHeader(type=5) + PbrHeader(spid=0, dpid=0x200) + [HBR bytes]

7. _route_packet(ingress_port=0, pbr_packet, "host_to_target")
   base_packet.is_pbr() == True  →  PBR path

8. PbrSwitchManager.get_drt(drt_index=0, dpid=0x200, num=1)
   → DrtEntry(PHYSICAL_PORT, routing_target=2)

9. inner_packet = pbr_packet._inner_packet  (zero-copy)

10. port_fifos[2].host_to_target.put(inner_packet)

11. GFD reads original HBR MWR TLP from its FIFO, processes normally.
```

---

### Q5.3 — Why is `ConfigurePidBindingCommand` implemented as a `CciBackgroundCommand`?

**Answer:**  
CXL Specification §7.7.13.7 explicitly mandates that PID binding requires link-state transitions:
> The bind operation triggers a Hot Reset → Detect → L0 sequence on the affected port.

This sequence cannot complete synchronously within a single CCI request-response cycle. `CciBackgroundCommand` returns an in-progress status immediately, and the completion is polled by the FM using a separate "background operation status" CCI command. This follows the same pattern as other long-running CXL commands (e.g., device sanitize, firmware update).

---

### Q5.4 — How does the PBR switch remain backward-compatible with existing HBR topologies?

**Answer:**  
The `CxlSwitchConfig` has `enable_pbr: bool = False`. When False:
- PBR CCI commands are not registered in `_initialize_mctp_endpoint()`.
- The Virtual Switch Manager (VSM) handles all routing via vPPB bindings (classic HBR).
- `PbrSwitchRouter` is never instantiated.

This means existing test suites, integration tests, and YAML topology configs that do not set `enable_pbr=True` are completely unaffected. There is no runtime branching in the packet processor itself — the PBR router is a separate, opt-in component running its own async task loop.

---

### Q5.5 — What happens when a packet arrives with a DPID that has no DRT entry?

**Answer:**  
In `PbrSwitchRouter._route_packet()`:

```python
drt_result = self._pbr_switch_manager.get_drt(0, dpid, 1)
if drt_result is None or not drt_result[0]:
    logger.warning(f"Drop: DPID 0x{dpid:x} not found in DRT")
    return   # packet is silently dropped
```

The DRT is initialized with all entries as `INVALID` type. A lookup for an unrouted DPID returns `None`. The packet is dropped (not forwarded to port 0 or anywhere else).

**Design rationale:** Returning `None` / dropping is the safe default — silently misrouting to port 0 could corrupt another device's memory space. The CXL spec permits this drop behaviour for unresolvable DPIDs.

## 6. Multi-Logical Device (MLD) Architecture

### Q6.1 — What is a Multi-Logical Device (MLD) and how is it modelled?

**Answer:**  
An MLD is a CXL Type-3 device that presents **multiple independent Logical Devices (LDs)** to the host over a single physical port. Each LD has its own:
- CXL.io config space (with a unique LD-ID)
- CXL.mem address range (partitioned by HDM decoders)
- Memory backing file

In `opencis-core`:
- `MultiLogicalDevice` (app layer) composes an array of `SingleLogicalDevice` instances.
- `CxlPacketProcessor` in `LD` mode maintains a list of `FifoGroup` entries (one per LD) and routes based on `tlp_prefix.ld_id`.
- `FMLD` handles the CCI sub-protocol that lets the FM query and set LD allocations.
- `MLDManager` (singleton) maintains a registry of port_index → MLD instance for dynamic creation/teardown.

---

### Q6.2 — How does the MLD packet processor route incoming CXL.io packets to the correct LD?

**Answer:**  
For requests (CFG_RD, CFG_WR, MRD, MWR), the LD-ID is in the TLP prefix:

```python
if self._component_type == CXL_COMPONENT_TYPE.LD:
    ld_id = cxl_io_packet.tlp_prefix.ld_id
    await self._incoming[ld_id].cfg_space.put(cxl_io_packet)
```

For completions (CPL, CPLD), the TLP table maps the transaction-ID+LD-ID back to the originating FIFO type:

```python
fifo_type = self._pop_tlp_table_entry(cxl_io_packet)
ld_id = cxl_io_packet.tlp_prefix.ld_id
if fifo_type == CXL_IO_FIFO_TYPE.CFG:
    await self._incoming[ld_id].cfg_space.put(cxl_io_packet)
```

For CXL.mem, routing uses the `ld_id` embedded in the M2S/S2M packet headers:

```python
if cxl_mem_packet.is_m2sreq():
    ld_id = cxl_mem_packet.m2sreq_header.ld_id
await self._incoming[ld_id].cxl_mem.put(cxl_mem_packet)
```

---

### Q6.3 — Describe the `MLDManager.sync_with_switch_state()` algorithm and its limitations.

**Answer:**  
`sync_with_switch_state()` reconciles the MLD Manager's in-memory device list with the LD allocation state reported by the switch (via FMLD CCI responses).

**Algorithm:**
1. If switch reports 0 LDs → clear all manager devices.
2. If manager has MORE devices than switch → identify excess by extracting LD-ID from device labels (regex `LD(\d+)`), remove those not in `switch_ld_ids`.
3. If manager has FEWER devices than switch → log warning; cannot create missing devices during sync (only the normal allocation API path can create them).
4. If counts match → verify LD-ID sets match; log warning on mismatch.

**Limitations identified in the code:**
- The label parsing (`re.search(r"LD(\d+)", label)`) is fragile — any label format change breaks sync.
- `get_fmld_allocation_state()` is marked `TODO` — actual FMLD state is not yet queried.
- Missing devices during sync produce only a log warning, not an error or exception.

## 7. Cache Coherency

### Q7.1 — What MESI states does the cache controller implement and how are state transitions triggered?

**Answer:**  
The `CacheController` implements four states (`CacheState`):

| State | Meaning |
|---|---|
| `CACHE_INVALID` | Block not cached |
| `CACHE_SHARED` | Cached, read-only, may exist in other caches |
| `CACHE_EXCLUSIVE` | Cached, read-only, known unique copy |
| `CACHE_MODIFIED` | Cached, dirty, must write back before eviction |

**Transition triggers:**

- **Load hit on SHARED** → remain SHARED.
- **Store hit on SHARED** → send `SNP_INV` to coherency agent → transition to EXCLUSIVE → MODIFIED.
- **Load miss** → send `SNP_DATA` to coh agent; response `RSP_S`→SHARED, `RSP_E`→EXCLUSIVE, `RSP_M`→MODIFIED.
- **Eviction of MODIFIED** → send `WRITE_BACK` with dirty data → transition block to INVALID.
- **Snoop from coh agent** → `SNP_INV` forces INVALID; `SNP_DATA` forces SHARED; `SNP_CUR` leaves state unchanged.

---

### Q7.2 — How does the cache controller handle the dual role of host-side vs device-side?

**Answer:**  
`CacheController` is configured via `CacheControllerConfig`. When `processor_to_cache_fifo` is `None`, it operates in **device-side mode** (no processor, coh agent only). When set, it operates in **host-side mode**.

Host-side adds a second routing dimension: address type determines which coherency fifo to use:

```python
def _get_cache_fifo(self, addr: int) -> CacheFifoPair:
    addr_type = self.get_mem_addr_type(addr)
    match addr_type:
        case MEM_ADDR_TYPE.DRAM:
            return self._cache_to_coh_bridge_fifo    # local DRAM coherency bridge
        case MEM_ADDR_TYPE.CXL_CACHED | CXL_CACHED_BI:
            return self._cache_to_coh_agent_fifo     # CXL device coherency agent
```

`CXL_CACHED_BI` (back-invalidate capable) additionally triggers `SNP_INV` before any write to ensure device-side caches are invalidated.

---

### Q7.3 — What is the eviction policy and how is LRU approximated?

**Answer:**  
The cache uses a **pseudo-LRU** policy via a monotonic priority counter per set:

```python
def _cache_priority_update(self, set: int, blk: int):
    self._cache[set][blk].priority = self._setcnt[set].counter
    self._setcnt[set].counter += 1
```

On every hit or fill, the block's priority is updated to the current counter value. On eviction, the block with the **lowest priority** (least recently accessed) is chosen:

```python
def _cache_find_replace_block(self, set: int) -> Tuple[int, CacheState]:
    min_priority = self._cache[set][0].priority
    min_idx = 0
    for idx in range(1, self._cache_assoc_size):
        if self._cache[set][idx].priority < min_priority:
            min_priority = self._cache[set][idx].priority
            min_idx = idx
    return min_idx, self._cache[set][min_idx].state
```

This is an O(N) scan per eviction (N = associativity, default 4). For a simulator this is acceptable; a real cache would use tree-PLRU bitmasks for O(1) replacement.

## 8. Fabric Manager & Control Plane

### Q8.1 — How does the Fabric Manager communicate with the switch?

**Answer:**  
Two-tier communication:

```
FM CLI (browser/Python) 
    ↕ Socket.IO (HTTP, port 8200)
FabricManagerSocketIoServer
    ↕ calls MctpCciApiClient methods
MctpCciApiClient
    ↕ TCP raw bytes (port 8100) — CCI packets
MctpCciExecutor (inside CxlSwitch)
    ↕ dispatches to registered CciCommand handlers
```

- **Socket.IO** provides a JSON API for human operators and test scripts.
- **MCTP CCI** is the actual CXL spec protocol: binary packets with opcode, payload length, and return code.
- `MctpCciExecutor` dispatches purely by opcode to registered handler objects — no hardcoded switch statement. New commands (e.g., PBR) are registered by calling `register_cci_commands([...])` during switch initialization.

---

### Q8.2 — What is the CCI command registration pattern and how does it enable extensibility?

**Answer:**  
Each CCI command is a class that inherits from `CciCommand` (or `CciBackgroundCommand`). It implements `_execute()` which contains the business logic. Commands are registered with the executor at startup:

```python
# cxl_switch.py
def _initialize_mctp_endpoint(self):
    commands = [VirtualSwitchCommand(), ...]
    if self._config.enable_pbr:
        commands += [
            IdentifyPbrSwitchCommand(self._pbr_switch_manager),
            ConfigurePidAssignmentCommand(self._pbr_switch_manager),
            SetDrtCommand(self._pbr_switch_manager),
            ...
        ]
    self._mctp_executor.register_cci_commands(commands)
```

`MctpCciExecutor.dispatch(opcode, payload)` does a dict lookup: `self._command_registry[opcode]`. This is the **Command Pattern** combined with **Open/Closed Principle**: adding new commands requires no modification to the executor.

### Q8.3 — How does the FM CLI Socket.IO server bridge JSON commands to binary CCI packets?

**Answer:**

```python
# socketio_server.py — example for pbr:setDrt
async def _pbr_set_drt(self, sid, data):
    entries = [DrtEntry(
        entry_type=DrtEntryType[e["entryType"]],
```

The Socket.IO handler:

## 9. Concurrency & Async Architecture

### Q9.1 — Why was asyncio chosen over threading or multiprocessing?

**Answer:**

| Criterion | asyncio | threading | multiprocessing |
|---|---|---|---|
| Context switch cost | Near-zero (cooperative) | ~microsecond (OS scheduler) | Millisecond (fork/IPC) |
| Shared state safety | Single-threaded → no locks needed | Requires locks (GIL partial protection) | Requires IPC mechanisms |
| Hardware modelling | Naturally models event-driven hardware | Less natural fit | Overkill for a simulator |
| Python GIL | Not an issue (no true parallelism needed) | GIL limits CPU parallelism | Bypasses GIL but high overhead |

The simulator models hardware event loops (packet arrives → process → respond). asyncio queues directly model hardware FIFOs. The GIL is not a concern because the bottleneck is logical correctness, not raw compute throughput.

---

### Q9.2 — How does `PbrSwitchRouter` manage per-port tasks and clean shutdown?

**Answer:**  
Each physical port gets its own coroutine watching a FIFO:

```python
async def _run(self):
    for i, fifo in enumerate(self._port_fifos):
        if self._port_types[i]:   # USP
            self._routing_tasks.add_task(
                self._process_port_host_ingress(i, fifo)
            )
        else:                      # DSP
            self._routing_tasks.add_task(
                self._process_port_ingress(i, fifo)
            )
    await self._change_status_to_running()
    await self._routing_tasks.wait_for_completion()
```

Clean shutdown via `_stop()`:

```python
async def _stop(self):
    for fifo in self._port_fifos:
        await fifo.host_to_target.put(None)
        await fifo.target_to_host.put(None)
```

Sending `None` as a sentinel causes each per-port `while True:` loop to `break` on `if packet is None:`, and `AsyncGatherer.wait_for_completion()` then unblocks.

---

### Q9.3 — What potential deadlock scenario exists in the FIFO-based design, and how is it mitigated?

**Answer:**  
**Scenario:** Component A is waiting for a response on queue Q1, while Component B is blocked trying to put a response on Q1 because Q1 is full (bounded queue), while Component B cannot drain Q1 because it is waiting for a response from Component A on Q2.

**Mitigation strategies used in opencis-core:**
1. **Unbounded queues** (`asyncio.Queue()` with no `maxsize`) — puts never block, eliminating the "full queue" scenario. The trade-off is unbounded memory growth under extreme load.
2. **Separate queues per channel** — CFG, MMIO, CXL.mem, CXL.cache, CCI all have independent FIFOs. A slow consumer on one channel doesn't starve others.
3. **Disconnection notification fan-out** — on TCP disconnect, `_notify_outgoing_processors()` puts `CONNECTION_DISCONNECTED` on ALL outgoing queues simultaneously, unblocking all waiting consumers.

---

### Q9.4 — How is the `asyncio.gather()` pattern used, and what are its failure semantics?

**Answer:**  
`CxlPacketProcessor._process_outgoing_packets()` uses `gather()` to run all outgoing FIFO processors concurrently:

```python
tasks = [
    create_task(self._process_outgoing_cfg_packets()),
    create_task(self._process_outgoing_mmio_packets()),
]
if self._outgoing.cxl_mem:
    tasks.append(create_task(self._process_outgoing_cxl_mem_packets()))
...
await gather(*tasks)
```

**Failure semantics:** By default, if any task raises an exception, `gather()` propagates the first exception and cancels remaining tasks. In this codebase, each FIFO processor has its own `try/except` that catches all exceptions, sends a disconnection notification, and returns normally — so `gather()` always sees clean exits. This trades crash-fast behaviour for graceful teardown, appropriate for a network simulator.

## 10. Testing Strategy

### Q10.1 — Describe the three testing tiers available for PBR features.

**Answer:**

| Tier | Script | Requires | Speed | Coverage |
|---|---|---|---|---|
| **Standalone in-process** | `pbr_standalone_test.py` | Nothing | ~100ms | 27 checks, CCI command handlers direct |
| **pytest unit + integration** | `pytest tests/test_pbr_*.py` | Nothing | ~0.5s | 47 tests: command set + data-plane routing |
| **Live switch over MCTP** | `pbr_cli_test.py --mctp-host ...` | Running switch | ~2–5s | 6 smoke tests: full TCP path |

**Philosophy:** The Standalone tier validates the business logic completely in-process. The pytest tier adds the asyncio event loop, TCP sockets, and packet serialization. The live tier adds real OS networking. Each tier builds confidence without requiring heavier infrastructure.

### Q10.2 — How are asyncio tests structured in this project?

**Answer:**  
Tests use `pytest-asyncio` with `asyncio_default_fixture_loop_scope = "session"` (one event loop per test session). Fixtures typically:

1. Create and wire up component instances.
2. Call `asyncio.create_task(component.run())` to start the component.
3. Await `component.wait_for_ready()` before exercising the component.
4. Enqueue test packets and await expected responses.
5. Call `await component.stop()` in teardown.

The `conftest.py` defines shared topology fixtures (switch + devices + connections) so individual test files focus only on the scenario being tested.

## 11. Performance & Optimization

### Q11.1 — What are the main performance bottlenecks in the simulator and how are they addressed?

**Answer:**

| Bottleneck | Impact | Mitigation |
|---|---|---|
| Packet field bit manipulation | High — every TLP accesses multiple fields | Cython `.pyx` compiled extension; pure-Python fallback for dev environments |
| Python asyncio event loop overhead | Medium — coroutine switching per packet | Batching not used; design favors latency over throughput (appropriate for a simulator) |
| Backing memory file I/O | Medium — every CXL.mem read/write hits a file | `mmap` or in-memory `bytearray` for memory files; binary `.bin` files pre-allocated |
| TLP table dict lookup | Low — O(1) hash lookup per in-flight transaction | Negligible; Python dict is highly optimized |
| `gather()` task creation overhead | Low — one call per component start | Tasks are long-lived coroutines, `create_task()` is a one-time cost |

---

### Q11.2 — How would you scale this simulator to handle thousands of concurrent CXL devices?

**Answer:**  
Current design limitations and scale-out strategies:

1. **Single-threaded asyncio** → Use `asyncio.run_coroutine_threadsafe()` with multiple event loops in separate threads, one per logical "rack segment".
2. **In-process component graph** → Move to **multiprocessing** with shared-memory IPC for the FIFO queues (e.g., `multiprocessing.Queue` or `mmap`-based ring buffers).
3. **Pure-Python packet structs** → Ensure Cython extension is compiled in production; profile hot paths with `cProfile`.
4. **Unbounded queues** → Add backpressure with bounded `asyncio.Queue(maxsize=N)` and handle `QueueFull` exceptions gracefully.
5. **Single MLDManager singleton** → Replace with a distributed registry (Redis or etcd) for multi-process scenarios.

### Q12.2 — How would you add a new CXL CCI command to the framework?

**Answer:**  
Step-by-step following the established pattern:

1. **Add opcode** to `CCI_FM_API_COMMAND_OPCODE` in `opencis/cxl/cci/common.py`.
2. **Create command file** in `opencis/cxl/cci/fabric_manager/<subsystem>/new_command.py`:
   - `NewCommandRequestPayload` dataclass with `dump()` and `parse()`.
   - `NewCommandResponsePayload` dataclass (if applicable).
   - `NewCommandCciCommand(CciCommand)` implementing `_execute(self, request)`.
   - Static `create_cci_request()` and `parse_response_payload()` helpers.
3. **Register** in `CxlSwitch._initialize_mctp_endpoint()`.
4. **Add API client method** to `MctpCciApiClient` for the FM to call.
5. **Add Socket.IO handler** in `FabricManagerSocketIoServer` if operator-facing.
6. **Write unit tests** following the pattern in `tests/test_pbr_switch_command_set.py`.

The executor picks up the new command automatically via opcode dispatch — no changes to the dispatcher itself.

### Q12.3 — What observability mechanisms does the simulator provide?

## Summary: Key Architectural Decisions

| Decision | Rationale |
|---|---|
| asyncio over threading | Hardware models event-driven; single-thread avoids locks |
| Queue-based inter-component comms | Decoupled, testable, models real CXL credit channels |
| `RunnableComponent` base class | Uniform lifecycle: start, wait_for_ready, stop |
| TLP table for in-flight tracking | Correctly demuxes completions to CFG vs MMIO FIFO |
| `enable_pbr=False` default | Zero-impact backward compatibility for HBR topologies |
| Zero-copy PBR decapsulation | Avoids re-parsing bytes for in-process simulation paths |
| Separate HDM decoder vs PBR manager | Data plane (address→DPID) vs control plane (CCI state) |
| Code-generated packet structs | Single field definition drives both Cython and pure-Python |
| Per-command CCI handler classes | Open/Closed; independently testable; mirrors spec structure |
| Stateless PBR switch manager | CXL FM model: FM re-programs all state on reconnect |
